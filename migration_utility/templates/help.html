Discovery

Workflow

The Discovery module scans your SQL Server source (or built-in demo objects) and performs deep analysis on every Stored Procedure, View, and UDF. It generates complexity scores, migration readiness assessments, root-cause analysis, and a dependency graph — giving stakeholders clear visibility before a single line of code is converted.

Discovery pane — KPI cards, Bill of Materials, complexity charts & dependency graph

How It Works

Select Source — Choose "Static Demo Objects", "Live SQL Server (ODBC)", or "Both" from the dropdown.

Run Discovery Scan — Click the scan button. The engine analyses every SQL object using 15+ regex patterns detecting CTEs, cursors, temp tables, MERGE, dynamic SQL, window functions, PIVOT, TRY-CATCH, transactions, CROSS APPLY, and more.

Review KPI Cards — 12 cards show total objects, type breakdown (SPs / Views / UDFs), complexity tiers (Simple / Moderate / Complex / Very Complex), story points, average complexity, auto-convert readiness %, and high-risk count.

Filter the BOM Table — Search by name, filter by type, tier, or risk level. Click any row to open the RCA panel.

Analyse Charts — A doughnut chart shows tier distribution; a horizontal bar chart ranks the top 15 objects by complexity score.

Explore Dependencies — The D3.js force-directed graph shows object-to-object and object-to-table relationships. Drag nodes, click for RCA details.

Export — Download a self-contained HTML report or a CSV Bill-of-Materials.

🔍 Complexity Scoring

Additive scoring: cursors (+15), dynamic SQL (+15), MERGE (+10), temp tables (+5 each), CTEs (+3), and more. Total maps to Simple/Moderate/Complex/Very Complex tiers.

📋 Bill of Materials

Full inventory table with name, type, lines, params, table refs, score, tier, effort hours, risk level, and migration readiness.

🔗 Dependency Graph

D3.js interactive force-directed graph. Nodes sized by complexity, coloured by type, with clickable RCA detail panels.

🩺 Root Cause Analysis

Per-object RCA showing which constructs cause complexity, their migration impact, why they're hard to convert, and unsupported PySpark patterns.

⚡ Risk Assessment

Risk factors detected: cursor usage, dynamic SQL, OPENQUERY, GOTO, excessive temp tables. Risk levels: Low / Medium / High / Critical.

📊 Effort Estimation

Each tier maps to effort hours (4-8h Simple, 8-16h Moderate, 16-24h Complex, 24-40h Very Complex) and story points for sprint planning.

💡
Tip: Run Discovery before Convert to PySpark — it helps you prioritise simple objects for quick wins and flag complex ones for manual review.
⚠️
Live source: Requires an active ODBC connection. Configure server, database, and credentials in Settings first. Discovery will scan sys.procedures, sys.views, sys.objects, and sys.sql_expression_dependencies.

Convert to PySpark

Core

The heart of the migration. This module connects to your SQL Server source, discovers Stored Procedures, Views, and UDFs, and converts them to Databricks-compatible PySpark notebooks using automated transformation.

Convert pane — Source connection, object selector, and converted PySpark code viewer

How It Works

Connect to SQL Server — Enter your server, database, and credentials in the Source Connection card. Supports Windows and SQL Authentication.

Discover Objects — Click "Fetch Objects" to scan for Stored Procedures, Views, and UDFs. The KPI pills at the top show totals.

Select Objects — Use checkboxes to pick which SQL objects to convert. Use "Select All" or filter by type.

Convert — Click "Convert Selected" to transform SQL code into PySpark. Each object becomes a separate `.py` notebook.

Review & Edit — View converted code in the syntax-highlighted editor. Make manual edits if needed before deploying.

🔗 Source Connection

SQL Server connection with server name, database, user/password, and optional Windows Auth toggle.

🔍 Object Discovery

Automatic discovery of SPs, Views, and UDFs with counts displayed in KPI stat pills.

🤖 Conversion

Intelligent SQL-to-PySpark conversion handling joins, CTEs, temp tables, cursors, and complex patterns.

📝 Code Viewer

Dark-themed syntax-highlighted code editor with copy, download, and inline editing capabilities.

💡
Tip: UDFs are automatically bundled into a single HelperFunction.py notebook for reuse across all converted notebooks.

Job Scheduler

Workflow

Schedule recurring job runs with cron expressions or user-friendly time pickers. Manages timezone settings, pause/resume schedules, and integrates with the Databricks Jobs API.

Job Scheduler — Configure schedules with cron, timezone selector, and edit capabilities

Select Job — Choose from the list of existing Databricks Jobs.

Set Schedule — Use the cron builder or manual input. Supports standard cron (5 fields) and Quartz (6-7 fields).

Azure DevOps — Git Integration

DevOps

Push Data Model DDL scripts, ER diagram images (PNG), and model JSON to an Azure DevOps Git repository directly from the Data Modeling module. Uses PAT authentication stored securely in Azure Key Vault.

Azure DevOps Integration — Push DDL & ER diagrams to Git with Key Vault PAT

Configure Settings — In Settings → Azure DevOps section, enter Organization, Project, Repository, and Branch name.

Store PAT in Key Vault — Store your Azure DevOps Personal Access Token as devops-token secret in Azure Key Vault (e.g. kv-dbxmigrator-west3).

Test Connection — Click "Test Connection" to verify the PAT and repo access. A green success message confirms connectivity.

Generate Model — Go to Data Modeling, generate your Star/Snowflake schema, and review the ER diagram and DDL.

Push to DevOps — Click the "Push to DevOps" button in the ER Diagram toolbar. Enter a commit message and the files are committed atomically.

🔗 One-Click Git Push

DDL (.sql), ER diagram (.png), and model (.json) are pushed in a single atomic commit to your configured branch.

🔐 Key Vault Security

PAT is never stored in config or UI — resolved at runtime from Azure Key Vault secret devops-token.

🌿 Auto Branch Creation

If the target branch doesn't exist, it's automatically created from the default branch (usually main).

✅ Test Connection

Validates organization, project, repo, and PAT before pushing — shows repo name and default branch on success.

Configuration Fields:
  • Organization — Azure DevOps org name (e.g. EMEA-SalesOps) or full URL
  • Project — Project name (e.g. AI Accelerator)
  • Repository — Git repository name
  • Branch — Target branch (auto-created if missing, defaults to data-modeling)
  • PAT — Stored in Key Vault as secret name devops-token
