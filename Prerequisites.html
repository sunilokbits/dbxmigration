1.1 Application Package & Release Artifacts

Versioned, tested, and sign-off ready
0%
Release-tagged application source bundle
Git-tagged / versioned copy of DBXMigrationApp containing app.yml, databricks.yml, migration_utility/, requirements.txt, and resources/. No local-only or debug files included.
CRITICALOUR SIDE
Pinned & tested requirements.txt
All Python dependencies (Flask, gunicorn, databricks-sql-connector, databricks-sdk, azure-*, snowflake / redshift connectors) pinned to versions validated in QA. Confirmed compatible with the Databricks Apps runtime (Python 3.11+).
CRITICALOUR SIDE
QA / UAT sign-off on the release build
All panes verified: Settings, Discovery, MetadataFlow, Pipeline Studio, Job Manager/Scheduler, Reports, Progress Tracker, Schema Comparison, Reconciliation, Data Quality, Data Modeling, Health Check, Audit.
HIGHOUR SIDE
Release notes & known-issues list
Feature summary, fixes included, known limitations (e.g. live profiling limited to SQL-family sources), and workaround notes.
MEDIUMOUR SIDE
Deployment runbook & rollback plan
Step-by-step deploy (databricks bundle deploy / Apps UI), environment variable matrix per client, and a tested rollback procedure (previous app version / bundle target).
HIGHOUR SIDE

1.2 Application Configuration Matrix

Per-client environment values — agreed, not improvised on deploy day
0%
Client-specific app.yml environment matrix
Final values agreed with client: DATABRICKS_CATALOG, DATABRICKS_SCHEMA, DATABRICKS_SECRET_SCOPE, DATABRICKS_SERVER_HOSTNAME, DATABRICKS_HTTP_PATH / DATABRICKS_SQL_WAREHOUSE_ID, CLOUD_PROVIDER=azure, unique FLASK_SECRET_KEY, cache limits (CATALOG_CACHE_TTL, MAX_TABLES_PER_SCHEMA).
CRITICALOUR SIDE
AI / Genie serving endpoints mapped for the client
The app references model-serving endpoints (databricks-claude-opus, -sonnet, -haiku families) for Genie AI features. Confirm client-approved equivalents exist in their workspace and update app.yml resource names + CAN_QUERY permissions accordingly — or agree to disable AI features at launch.
CRITICALOUR SIDE
Catalog / schema naming convention sheet
Mapping of logical layers (landing, bronze, silver, reconciliation, logging, admin/config) to the client's Unity Catalog names — matches the bundle variables in databricks.yml (dev / staging / prod targets).
HIGHOUR SIDE
Generated notebook templates validated
Extract / Bronze / Silver / Orchestrator metadata notebooks (Standard PySpark + DLT/SDP variants) tested against the release, including DQ metrics (__dq_metrics) output.
MEDIUMOUR SIDE

1.3 Deployment Capability & Access

What we need from the client to execute the deployment
0%
Deployment identity provisioned in client workspace
Either a named workspace user or service principal granted Workspace Admin (or CAN_MANAGE on Apps + UC creation rights) for the deployment window, plus CAN_USE on the SQL Warehouse and CAN_QUERY on AI endpoints.
CRITICALOUR SIDE
Databricks CLI + toolchain ready
Databricks CLI ≥ 0.215 (bundle support), Python 3.11/3.12, authenticated profile for the client workspace (databricks auth login or SP with OAuth secret). Network access to *.azuredatabricks.net from the deployment machine.
HIGHOUR SIDE
Smoke-test script & validation dataset
Automated post-deploy checks: app health /api/v1/… 200, metadata table creation, source connection test, pilot table migration, DQ metric write. Plus a small demo dataset for the client acceptance walkthrough.
HIGHOUR SIDE
Handover pack
Architecture diagram, admin guide, end-user quick-start, this prerequisites document, support model & escalation matrix, and a recorded walkthrough / accelerator video.
MEDIUMOUR SIDE
Client environment responsibilities. Delays in these items are the most common cause of deployment slippage — please assign an owner and target date to each section before kickoff.

2.1 Azure Subscription & Databricks Workspace

Foundation — without these nothing deploys
0%
Azure subscription with capacity & billing
Active subscription, quota for Azure Databricks + serverless, budget/alerts configured. Data-residency region agreed (workspace region must support Databricks Apps, Serverless SQL Warehouse, and Model Serving if AI features are in scope).
CRITICALCLIENT SIDE
Azure Databricks Premium workspace
Databricks Apps require the Premium plan. Workspace accessible to the deployment identity; Apps feature available (not blocked by workspace allow-list / IP-access policies being finalised).
CRITICALCLIENT SIDE
Serverless SQL Warehouse created & running
A SQL Warehouse (serverless recommended) for all app queries and generated pipelines. Share the Warehouse ID / HTTP Path with the delivery team. The app identity needs CAN_USE on it.
CRITICALCLIENT SIDE
Job / pipeline compute allowance
Permission to create Jobs and (if not serverless) clusters for the deployed metadata pipelines; cluster policies that permit the required VM sizes; serverless jobs enabled where available.
HIGHCLIENT SIDE

2.2 Unity Catalog, Storage & Landing Zone

Where migrated data and app metadata will live
0%
Unity Catalog metastore attached to the workspace
UC enabled with an assigned metastore. App service principal granted USE CATALOG / USE SCHEMA / CREATE SCHEMA / CREATE TABLE on the catalogs below (or workspace-level metastore privileges via an admin group).
CRITICALCLIENT SIDE
Catalogs provisioned (or creation rights granted)
Six logical catalogs: admin_source (app config & metadata tables), bronze, silver, dev_volumes (landing volumes), reconciliation, loggingdetails — or client-named equivalents recorded in the config matrix.
CRITICALCLIENT SIDE
ADLS Gen2 storage account + container
Storage account with hierarchical namespace enabled and a dedicated container (e.g. datalake) for landing / staging data.
CRITICALCLIENT SIDE
Access connector & storage credential
Azure Databricks Access Connector with Storage Blob Data Owner (or Contributor) role on the storage account, plus a UC Storage Credential referencing it.
CRITICALCLIENT SIDE
External locations & landing volume
UC external location over the container and a Volume for the landing path (e.g. abfss://datalake@<account>.dfs.core.windows.net/<env>/landing). Path shared for the app Settings.
HIGHCLIENT SIDE
Databricks secret scope created
Scope (default name migration-studio) created; app identity granted READ on it. Used for source passwords, DevOps PAT, and Databricks token storage.
HIGHCLIENT SIDE

2.3 Network, Firewall & Security

The #1 cause of failed source connections
0%
Source database firewall opened for Databricks
Azure SQL / Synapse: allow the SQL Warehouse / serverless compute egress IPs (or "Allow Azure services") so JDBC extraction works. On-prem SQL Server: firewall rules + gateway/VPN path for the Databricks egress range. Test with a connectivity probe before deployment day.
CRITICALCLIENT SIDE
Egress to external APIs allowed (if used)
Outbound access from serverless compute / app backend to login.microsoftonline.com (SharePoint tokens), *.sharepoint.com, and target REST API hosts.
HIGHCLIENT SIDE
IP access lists & SSO reviewed for the App URL
If the workspace enforces IP access lists, ensure business users' networks can reach the deployed App URL; SSO/Entra conditional-access policies tested with a pilot user group.
HIGHCLIENT SIDE
Security review & data-residency clearance
Client security team sign-off on: app service principal scopes, secret scope usage, data landing regions, and any use of external AI model endpoints (data-governance review for Genie AI features).
MEDIUMCLIENT SIDE

2.4 Source System Access & Credentials

Read-only accounts are sufficient — per source type
0%
SQL Server / Azure SQL / Synapse read account
SQL login with SELECT + VIEW DEFINITION on source database(s) (needed for procedures/views/UDFs discovery). Server name, database, username ready; password stored to the secret scope on the day.
CRITICALCLIENT SIDE
Snowflake access (if applicable)
Account identifier, user, password/keys, virtual warehouse (e.g. MIGRATION_WH) and a role with USAGE on warehouse + SELECT/REFERENCES on target databases.
HIGHCLIENT SIDE
Amazon Redshift access (if applicable)
Cluster endpoint + port, database, user credentials; security group allows Databricks egress.
HIGHCLIENT SIDE
SharePoint source (if applicable)
Entra ID app registration with client secret, Sites.Read.All (or scoped Sites.Selected) application permission + admin consent granted; tenant ID, client ID, and target site URLs documented.
HIGHCLIENT SIDE
REST API sources (if applicable)
Base URL(s), auth mode (API key / Bearer / Basic), credentials, and — ideally — an OpenAPI/Swagger URL for automated endpoint discovery.
MEDIUMCLIENT SIDE
Azure DevOps (optional — PR automation)
Organisation, project, repository, branch, and a PAT with Code (Read & Write) if generated notebooks should be pushed as pull requests for review.
MEDIUMCLIENT SIDE

2.5 Users, Roles & Governance

Who will use the app from day one
0%
App user list & role mapping
Named business/technical users with CAN_USE permission on the deployed App. Admin vs Developer roles agreed (app supports migration-studio-admins / migration-studio-developers group conventions).
HIGHCLIENT SIDE
Naming, tagging & cost governance
Resource naming convention, Azure tags, Databricks budgets/alerts for warehouse + jobs usage attributable to the migration project.
MEDIUMCLIENT SIDE

Deployment date/time, change ticket raised if required by the client's process, and named contacts for network / DBA / Databricks admin escalation during the window.
MEDIUMCLIENT SIDE

Phase 3 — End-to-End Validation (Pilot)

~60 min · One real table, every feature touched
