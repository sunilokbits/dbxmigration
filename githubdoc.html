01 — Architecture

The pipeline, end to end

One workflow file, three trigger paths. A PR only validates. A push to main deploys to dev automatically. A release/* tag fans out to every client, each behind its own approval.

03 — What's automatic vs. manual

Only two things are ever manual

1

Generating the bootstrap PAT

Someone creates one Databricks PAT per workspace, once, when onboarding it. Nothing can automate this — it's the credential needed to reach a workspace for the first time.

2

Approving a client release

The required reviewer on client-<name> clicks Approve. Everything downstream of that click — infra, secrets, Genie Space, the app — runs unattended.

◆

Unity Catalog infra

Storage, access connector, catalogs/schemas, the landing volume — created if missing, reused if not, by AutoInfraCreation.py.

◆

Secrets

The migration-studio Databricks secret scope is created and populated automatically — source DB password, per-client Flask key, DevOps PAT.

◆

Genie Space

Reused if genie_space_id is already set in the client config; otherwise auto-created via the Genie API.

◆

The Databricks App

databricks bundle deploy -t client creates or updates the app named dbxmigrationapp — same name in every workspace.

04 — Trigger reference

What causes what

Event Jobs that run Target Gate
pull_request → main validate none deployed none
push → main validate → deploy-dev dev none — fully automatic
workflow_dispatch (deploy_staging=true) validate → deploy-dev → deploy-staging staging manual trigger, no approval step
push tag release/* validate → deploy-clients (matrix) every client in CLIENTS_JSON required reviewer per client-<name>
05 — Quick reference

Core commands

$git push origin main# triggers validate + deploy-dev
$gh workflow run cicd.yml -f deploy_staging=true# manually add a staging deploy
$git tag release/1.0.0 && git push origin release/1.0.0# triggers the client fan-out
$gh run watch# follow the current run's live status
$git push origin :refs/tags/release/1.0.0# delete a bad tag (does not undo a deploy)
Rollback: re-tag the last known-good commit and push it as a new release/* tag — databricks bundle deploy reconciles state, so redeploying an older revision is safe.
