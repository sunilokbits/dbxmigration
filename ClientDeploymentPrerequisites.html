What has to exist in the target workspace before you run the deploy. one_click_deploy.py automates Unity Catalog infra, secrets, the Genie Space, and the app itself from just a PAT — but the PAT, the workspace, and a few things it genuinely can't do for you (client-side network/manual approvals) have to be ready first.

1.1 Deployment Identity & Credentials

One PAT per workspace — the only hard requirement to start
0%
Databricks PAT for the target workspace
A Personal Access Token belonging to a user/SP with workspace-admin-level rights (UC creation, secrets, Apps, Jobs). Set as DATABRICKS_TOKEN env var — never written into deploy/clients/<name>.json (that file is git-ignored but still meant to hold non-secret values only).
CRITICALCLIENT SIDE
Azure Service Principal (only if with_infra: true)
AZURE_CLIENT_ID / AZURE_CLIENT_SECRET / AZURE_TENANT_ID with Contributor + User Access Administrator on the target subscription/resource group. Omit all three (or pass --skip-infra) if Azure storage/UC infra already exists — then browser/CLI login is enough.
HIGHCLIENT SIDE
Source DB password / DevOps PAT ready as env vars
DBX_SOURCE_PASSWORD (skip entirely if no source DB is configured for this client) and optional DBX_DEVOPS_PAT for Push-to-DevOps. The script prompts (masked) if missing and you're running interactively — but CI (--yes) fails fast instead.
HIGHOUR SIDE
Client config JSON completed
cp deploy/client.template.json deploy/clients/<name>.json and fill every field: client_name, databricks_host, catalog_admin/app_schema, bronze/silver/volumes/recon/logging catalogs, azure block, source block. Remove the _comment key once done as a visual "reviewed" marker.
CRITICALJOINT

1.2 Workspace, Unity Catalog & Warehouse

Foundation the automated steps build on top of
0%
Premium workspace with Databricks Apps enabled
Databricks Apps require the Premium plan. Confirm the Apps feature isn't blocked by a workspace allow-list or a not-yet-finalised IP access policy.
CRITICALCLIENT SIDE
Unity Catalog metastore attached
Without an assigned metastore, every catalog/schema/table step in init_app_tables.py/one_click_deploy.py fails outright — this is not something the deploy script can create for you.
CRITICALCLIENT SIDE
A registered external location (or a metastore with default storage)
Some metastores reject a bare CREATE CATALOG IF NOT EXISTS with no storage root even when the catalog already exists. The deploy scripts fall back to piggybacking on any existing external location's storage root — having at least one registered avoids a manual "ask a metastore admin to create the catalog" step.
HIGHCLIENT SIDE
SQL Warehouse exists (or infra step will create one)
Serverless recommended. sql_warehouse_id in the client config, or leave blank to auto-discover a running one at deploy time.
HIGHCLIENT SIDE
App's own Service Principal will be granted UC access — don't skip this
The deploy identity's PAT creates the catalog/tables, but the running App authenticates as its own Service Principal (or a stored PAT that can go stale). init_app_tables.py/one_click_deploy.py now runs GRANT USE CATALOG / GRANT USE SCHEMA, SELECT, MODIFY, CREATE TABLE to that SP automatically — confirm the deploy PAT itself has enough authority to grant (catalog owner or metastore admin), or this step silently no-ops and every config save fails with TABLE_OR_VIEW_NOT_FOUND post-deploy (see Post-Validation 3.2).
CRITICALOUR SIDE

1.3 Storage & Network — client-side, cannot be automated

The most common cause of a mid-deploy or post-deploy surprise
0%
ADLS Gen2 storage account + container (if with_infra: true)
Hierarchical namespace enabled, dedicated container (e.g. datalake). If it already exists, set with_infra: false / pass --skip-infra and just fill in the existing names.
HIGHCLIENT SIDE
Source database firewall opened for Databricks egress
Azure SQL/Synapse: allow the SQL Warehouse's egress (or "Allow Azure services"). On-prem: firewall/VPN path for the Databricks egress range. Test this before deploy day — a connectivity probe from the target workspace, not an assumption.
CRITICALCLIENT SIDE
IP access lists / conditional access reviewed for the App URL
If the workspace enforces IP allow-lists or Entra conditional access, confirm the pilot users' networks can actually reach the deployed App URL before go-live.
MEDIUMCLIENT SIDE

1.4 Steps the script genuinely can't do for you

Manual, one-time, per-workspace
0%
Genie Space — manual fallback
Auto-create via the Genie API is attempted first; if unsupported in this workspace/region, the script prompts for a manually-created Space ID (Databricks UI → Genie → New Space) and stops there when run non-interactively (--yes) with a clear warning instead of failing.
MEDIUMJOINT
External location / storage credential with no existing coverage
If neither an existing external location nor a metastore default storage root covers the target catalog's path, a metastore admin has to create it manually with an explicit managed location (CREATE CATALOG … MANAGED LOCATION '<abfss-path>') — the automated steps only ever piggyback on what already exists.
HIGHCLIENT SIDE
Azure DevOps PAT scopes (if Push-to-DevOps is in scope)
PAT needs Code (Read & Write) on the target org/project/repo; org/project/repo/branch/reviewers agreed and recorded in Settings before the pilot run.
MEDIUMCLIENT SIDE
Pilot user access (CAN_USE on the App)
Assign the pilot group/user CAN_USE on the deployed App and confirm SSO login works — the deploy script creates the App but doesn't manage end-user ACLs.
HIGHCLIENT SIDE
CI-based deploy (optional): GitHub Environment + secrets
If deploying via the deploy-clients GitHub Actions job instead of running the script by hand: create the client-<name> Environment with a required reviewer, add its DATABRICKS_HOST/DATABRICKS_TOKEN/CLIENT_CONFIG_JSON/optional secrets, and add <name> to the repo's CLIENTS_JSON variable.
MEDIUMJOINT
Run these immediately before kicking off the deploy. Every check here is meant to fail fast and cheap — catching a missing grant or a placeholder value now costs two minutes; catching it mid-bundle deploy costs a rollback.

2.1 Auth & Config Sanity

Confirm the inputs before the script touches anything
0%
PAT authenticates against the target host
The pre-flight phase of one_click_deploy.py checks this automatically — but a quick manual curl -H "Authorization: Bearer $DATABRICKS_TOKEN" https://<host>/api/2.0/preview/scim/v2/Me before running catches a copy-pasted wrong host/token instantly.
CRITICALJOINT
Client config JSON has no placeholder values left
No empty "" on required fields (databricks_host, catalogs, azure.subscription_id/resource_group/storage_account/access_connector if infra is in scope). A missing infra field silently skips the infra step rather than failing — verify intent, don't assume.
CRITICALOUR SIDE
databricks bundle validate passes for the client target
databricks bundle validate -t client --var="client_name=<name>" — catches bundle/variable errors before any real resource is touched.
HIGHOUR SIDE
No stale partial-deploy leftovers
If this is a re-run after a failed attempt: check for a half-created secret scope, catalog, or App with a mismatched name before re-running — every step is idempotent, but a renamed client or changed catalog name mid-attempt can leave an orphaned resource under the old name.
MEDIUMOUR SIDE

2.2 Infra & Connectivity Probes

Verify the target workspace is actually reachable and ready
0%
Metastore attached & reachable
databricks unity-catalog metastores summary (or the workspace UI) confirms a metastore is assigned before any catalog step runs.
CRITICALJOINT
At least one SQL Warehouse exists (or infra will create one)
If none exists and with_infra doesn't provision one, the warehouse-dependent steps (app tables, Genie, catalog listing) skip with a warning instead of failing loudly — confirm this is expected.
HIGHJOINT
Source system connectivity probe passed
From a notebook/cluster in the target workspace: raw TCP/JDBC reach to each configured source (SQL Server/Snowflake/Redshift/SharePoint/API) confirmed before deploy day — the classic firewall surprise happens here, not in the app.
CRITICALCLIENT SIDE
Deploy identity's PAT owner can actually GRANT on the target catalog
Confirm the PAT belongs to the catalog owner, a metastore admin, or a principal with MANAGE — otherwise the App-SP grant step (Access 1.2) silently no-ops and post-validation 3.2 will fail.
MEDIUMOUR SIDE
Run these right after the deploy report shows green. A successful deploy/reports/<client>-<timestamp>.json means every automated step ran — it does not by itself prove the app works end-to-end for a real user. These checks are the regression tests for the exact class of bug that's bitten this app before: durable config saves, live pipeline status, and notebook-deploy state.

3.1 App Is Actually Running

The basics — confirm before anything deeper
0%
App status = Running, opens and logs in via SSO
Open the App URL, confirm no startup errors in the app logs, and that a pilot user can authenticate.
CRITICALJOINT
Secret scope populated
Settings → Secret Vault (Admin) shows databricks-token, devops-pat, and every configured source-*-password key as present — not stuck on the REPLACE_ME scaffold placeholder for a key you expected to be real.
HIGHOUR SIDE

3.2 Config Actually Persists (durable save)

Regression check — a real incident on this app: config silently discarded on every redeploy
0%
Settings → Save Config shows no "Saved locally only" popup
If it appears, the App's own identity can't see app_config yet (TABLE_OR_VIEW_NOT_FOUND) — usually the SP grant from Access 1.2 didn't land. The write also falls back to a local deployconfig.json that Databricks Apps wipes on every SNAPSHOT redeploy, so this must show durable: true before go-live, not "close enough."
CRITICALJOINT
A saved setting survives a redeploy
Save any Settings field, trigger a no-op redeploy (or just wait for the next scheduled one), refresh — the value must still be there. This is the direct test for "config gets overwritten every deployment."
HIGHOUR SIDE
Grants confirmed via SHOW GRANTS
SHOW GRANTS ON SCHEMA <catalog>.<schema> in the SQL editor lists USE CATALOG/USE SCHEMA/SELECT/MODIFY/CREATE TABLE for the App's Service Principal client ID, not just the deploy identity.
MEDIUMOUR SIDE

3.3 Pipeline Run & Dashboard Sync

Regression check — a run can succeed on Databricks while the app's own status stays stuck
0%
Run one full pilot pipeline (Extract → SDP/Bronze/Silver) end-to-end
Pipeline Studio's group badge must flip all the way to SUCCESS after the run actually finishes — not stay on CREATED/RUNNING after Databricks itself shows the job/pipeline completed. A stuck badge means the completion write to the app's status table failed silently; re-running the same job after confirming the fix is deployed should resolve it.
CRITICALJOINT
Dashboard tiles & Audit Log reflect the same run
Workflow Manager Dashboard's SUCCEEDED/FAILED/TOTAL JOBS counts and the Audit & Compliance event log must show the pilot run's final status, not just its "created" event — all three surfaces read the same underlying table, so a mismatch here points at the same write-path bug as 3.3's first item.
HIGHJOINT
Downstream analytics render from the same pilot run
Reports, Progress Tracker, Data Quality, Schema Comparison, and Reconciliation all pick up the pilot table without errors.
MEDIUMJOINT

3.4 Deploy Notebooks & Push to DevOps

Regression check — a page that forgot it was already connected
0%
Deploy Notebooks shows Connected automatically
Land on the tab fresh (no manual "Test Connection" click) — it should already show workspace/cluster info using the credentials the app already has, not a static "Not Connected."
HIGHOUR SIDE
A conversion survives a tab switch / reload
Convert an object via Convert to PySpark, switch tabs (or reload), come back to Deploy Notebooks — "Ready to Deploy" and Push to DevOps must still see it, not demand re-conversion.
MEDIUMOUR SIDE
Push to DevOps lands in the expected repo/branch
If in scope: confirm the pushed notebooks appear under the agreed org/project/repo/folder and branch, with reviewers added if configured.
MEDIUMJOINT
